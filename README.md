# 家庭菜園を LLM で運用するダッシュボード ― 構成解説

> **このリポジトリは「家族用ダッシュボードの生成物」だけを置く公開ミラーです。**
> 実体（Python 生成スクリプト・Markdown データ・AI 作業手順書）は別の **private リポジトリ**にあり、
> ここに入るのは生成された **数枚の HTML（ダッシュボード本体は `kazokuyo.html`）** と、この README だけです。
> **`index.html` は意図的に置いていません**（ルート URL からダッシュボードへ辿れないようにするため）。
> `main.js` も `data/` も**ありません**（理由は §0）。**CI は「発行の自動化」にだけ使います**（§5）。
> この README は、AI や人が**仕組みを解析・再現できる**ように書いた構成解説で、
> **地名・観測所ID・個人を特定する情報や住居・接続系の情報は意図的に伏せてあります**（安全に共有可）。
> ライブ表示: https://uminomae.github.io/garden/kazokuyo.html （検索避け noindex・URL 直リンクで閲覧）。

---

## 0. まず前提の訂正（重要・ここを外すと解析が噛み合わない）

これは **JS の SPA ではない**。`main.js` も `data/` API も**無い**。
**CI（GitHub Actions）は 2026-07-30 に「発行の自動化」としてだけ足した**——**生成も無害チェックもローカルと同じスクリプト**で、CI 側に独自ロジックは無い（§5）。

| 一般的な想定 | この仕組みの実態 |
|---|---|
| `main.js` / フロントエンド framework | **無し**。クライアント JS はアコーディオン開閉の数行だけ |
| `data/` フォルダ・DB・API | **無し**。**Markdown ファイル群そのものが DB**（Git が唯一の永続層） |
| GitHub Actions / CI 公開 | **発行の引き金としてのみ使う**（2026-07-30 追加）。生成の実体は変わらず **Python スクリプトが HTML を生成 → 別 repo へ force-push**。**同じスクリプトを、AI エージェントが動く場所（手元の PC・クラウド実行）からも CI からも叩ける**という二重の経路 |
| リポジトリ = ソース | 公開 repo は**生成物の HTML 数枚だけ**。本体（Python・Markdown・手順書）は**別の private repo** |
| 記録・分析の知能 | **AI エージェント（Claude Code＝CLI）** が人と対話しつつ Markdown を更新する |

**一言で**: 「Markdown = データベース、Python = 静的サイトジェネレータ、AI エージェント = 記録/分析の作業者、force-push = 公開」。

## 1. 全体アーキテクチャ

### データの流れ（記録 → 分析 → 公開）

```
現場の観察（写真 / 口頭メモ）
   ↓  人は「見て伝える」だけ
AI エージェント（Claude Code）が対象を特定
   ↓
Markdown に追記         logs/YYYY/YYYY-MM.md（観察・作業／追記専用）
   ↓                    plants.md（株の台帳）・語彙マスタで表記統一
気象の実測を追記         thermal-data.tsv（日別 気温・日照・降水）
   ↓
分析（積算温度モデル）    Python で区間 GDD を較正 → 次作の収穫日を逆算
   ↓
作業見通しを再生成        todo.md（今後4週間・GO条件つき）
   ↓
家族ページを生成          Python が「無害な数ファイル」だけを 1枚 HTML に
   ↓  ← 無害チェック（2段ゲート）
公開                      別 public repo へ force-push（GitHub Pages）
```

ポイント: **単方向パイプライン**。正本は常に Markdown。HTML は毎回**使い捨てで再生成**する（状態を HTML 側に持たない）。

### ディレクトリ構成（サニタイズ）


## 2. 記録部分（Markdown as Database）

**ログの書式**（1エントリ＝作物×場所、事実と判断を必ず分離）:

```markdown
### キュウリ [畑（南東）]

- 事実: 定植から3〜4週間で開花確認。ツルが支柱に巻き付き始めた
- 判断: 葉色が黄緑→濃緑は活着のサイン。誘引・整枝の開始タイミング
- 次: 親づるは5〜6節で摘心を検討
```

- **追記専用**（過去ログは編集しない）＝ `grep` が安定し、監査・時系列が壊れない。
- **写真管理**: `assets/YYYY/YYYY-MM-DD-作物-状態.jpeg`。ログから相対リンク（画像は公開ページには載せない）。
- **メタデータ**: 語彙マスタ（`crops.md`/`places.md`）で表記統一。`plants.md` に株ごとの定植日・場所・品種。
- **気象**: アメダス日別（平均気温・日照・降水）を TSV に追記＝分析の生データ。

## 3. 分析部分（データで判断する）

- **LLM が読む単位** = 1ファイル1トピック。役割で分割し重複させない:
  - `temp-signals.md`＝日々の GO/WAIT 判断の型　`thermal.md`＝積算温度で数値逆算　`lessons.md`＝失敗と来年の条件。
- **★ ローカル前提を最優先で読む（一般論を防ぐ最重要ポイント）**: `context.md` ＝ **一般論・教科書どおりと違うこと**
  だけを集めた1枚。**特別な状況・環境依存・作業者の癖**が入る:
  - **手元資源**（毎日出る窒素源・自給できる刈草や落ち葉＝買わずに回せるもの）と、
    **手元に無いもの**（一般論では定番でもここには無い資材＝それ前提の案は最初から採れない）
  - **環境依存**（冷涼・やませで暖地基準の適期が合わない／畝数が足りない／開墾しながら進める）
  - **作業者の癖・制約**（端末はスマホ主体／マルチは枯れ草限定／はんだ不使用）
  - **なぜ最優先か**: LLM は放っておくと**平均的な栽培の教科書解**を出す。だが**判断・選択肢・最終意思決定を
    決めるのはこの場所固有の事情**の方。ここを読まない提案は、**余っている資材を死蔵させ、要らない買い物を勧め、
    現場で実行できない**。よって**参照順位を最上位**に置き、作付け・資材・購入を検討する**あらゆる場面で最初に読む**
    （手順書 `CLAUDE.md` の冒頭にも同じ規則を置いてある＝**ファイルを作るだけでは読まれない**ので導線もセットにする）。
  - 使い方・効能や数値の正本は各ファイルへリンクし、ここには「**何が普通と違うか**」だけを書く（重複させない）。
- **RAG しやすさ**: 見出し規約＋語彙マスタ＋TSV で構造化。ファイル粒度は「粗すぎず細かすぎず」。全文 grep とベクトル検索の両対応。
- **分析ロジック（積算温度 GDD）**: 実測 TSV → 生育イベント区間の GDD を計算して**較正定数**を更新 → 次作の初収穫・収穫終了を**逆算**（Python）。
  - 不調は体感でなくデータで要因分離（例: 徒長→発芽直後の日照を引く／不発芽→地温）。

```
# 例: 定植日と較正定数(425℃·日)から初収穫・収穫終了を逆算（付属の GDD スクリプト）
python3 garden-thermal.py project --transplant 2026-08-05 --target 425
#  → 初収穫 9/9（35日）・収穫終了 10/14頃（日最低が生育停止ラインを割る日）
```

## 4. 公開部分（静的・最小・検索避け）

- **HTML**: Python が「無害な6ファイル」だけを 1枚に束ねる。CSS インライン、ダークモード対応、入れ子アコーディオン。
- **JavaScript**: 最小限（`<details>` 開閉のみ）。フレームワーク無し＝寿命が長い。
- **検索**: あえて **noindex ＋ robots.txt** で検索避け（家族限定運用）。だから**URL は直接渡す**（検索では出ない）。
- **地図・区画表示**: 現状はテキストの畝表（早見表）。**物理レイアウトは非公開**（無害ゲートで除外）。
- **無害チェック（2段ゲート）** ＝ この仕組みの肝:

```python
# 1) allowlist: 家族ページに載せてよいソースはこの集合だけ（それ以外は生成を止める）
PUBLIC_ALLOWLIST = {"garden/harvest.md", "garden/bed-map.md", "garden/todo.md",
                    "garden/procurement.md", "garden/year-calendar.md", "garden/llm-guide.md"}
# 2) denylist: 生成物を走査し、個人特定情報や住居・接続に関わる情報を
#    1件でも検出したら「書き出さず中止」。build 時と publish 直前の両方で実行。
```

## 5. 公開の仕組み（GitHub Pages・履歴を残さない）

- **private repo は絶対に push しない**。生成した HTML だけを**別の public repo** へ置く。
- 発行のたびに `.git` を作り直し、**親を持たない単一コミットで force-push**。
  - 目的: ぼかす前の古い版（地名など）が**公開の git 履歴に残らない**ようにする。public のコミットは常に1個。
- **発行経路は2つある**（どちらも同じ `publish-family-page.sh` を呼ぶ＝挙動が分岐しない）:
  1. **AI エージェント CLI から1コマンド**（ローカル／クラウド実行）＝対話の流れでその場で出せる
  2. **CI（GitHub Actions）**＝private repo の `main` に、家族ページに載るファイルが push されたら自動で発行
- **★2 を 2026-07-30 に足した理由＝1 だけではスマホ単体で完結しなかった**。
  この README は以前「Actions は使わない・既にスマホだけで回る」と書いていたが、**実際には次で詰まった**:
  - **クラウド実行で公開 repo がセッションのスコープ外だと、git がプロキシに書き換えられて 403**（2026-07-29 に実際に発行できず止まった）
  - **サンドボックス内では keychain に届かず TLS が落ちる**（認証情報を持つ経路がそこに無い）
  → **CI は「認証情報を、常にそれを持っている場所に置く」ための解**。**push さえできれば発行は勝手に追いつく**。
- **CI を足しても秘匿リスクが増えないようにした**（以前 "リスクが増えるだけ" と書いた懸念への回答）:
  - **無害チェックは CI でも二重ゲートのまま**。しかも**トークンを使う前に生成＋チェックだけを単独で走らせる**
    ＝**危ない中身を持ったまま認証情報を握る状態を作らない**。落ちれば push されない。
  - **認証はデプロイキー（SSH）で、効く範囲は公開 repo 1個だけ**。private repo 側へは書けない（アカウント全体に効く PAT を使わない）。
  - **CI 用の抜け道（`--force` 相当）は作っていない**。ゲートは1つでも検出したら非ゼロ終了する。
  → **端末に開発環境は要らない**（スマホから push、または AI エージェントのクラウド実行）。

## 6. 品質管理（壊れていないことを機械で確かめる）

**この仕組みは「Markdown＝DB／Python＝関数／HTML＝出力」という決まった形のアプリ**なので、
検査も定型化できる。**無害ゲート（§4）は「出してよいか」しか見ない**ので、
「**表示が黙って壊れていないか**」「**仕組みが噛み合っているか**」は別に持つ必要がある。
以下は**実際に壊してから足したもの**＝再現する人がそのまま使える形で置く。

**影響マップとテストの段**。「どこを編集したら、どこが壊れるか」を1枚に固定し、
**触った層のぶんだけ**検査を通す（毎回すべては通さない）:

| 段 | 何を触った時 | 通す検査 |
|---|---|---|
| **L0** | `garden/*.md`（データ）だけ | 整合性チェック（語彙×ログ×台帳）＋結合点チェック |
| **L1** | 変換層（Markdown→HTML）・CSS | **生成物の前後差分**（節の増減）＋出力スモーク＋**実機描画** |
| **L2** | 公開境界（allowlist・禁止パターン・ぼかし・掲載一覧・CI 発火条件） | 三点一致＋地名の往復テスト＋発行の手前まで通す dry-run |

**機械で見ている結合点**:

- **[A] 三点一致** … **「何を出すか」「何を許すか」「何が push されたら自動発行するか」の3つは同じ集合を指す**。
  1つに足し忘れると「**更新したのに公開が古い。エラーも出ない**」。3つを突き合わせて差を出す。
- **[B] ぼかしと禁止パターンの対** … 地名を**ぼかす**仕組みと**見つけたら止める**仕組みは、
  片方だけだと**素通り**か**毎回発行が止まる**。**両側から語を取り出して往復で照合**する。
- **[C] 出力スモーク** … 生成できるか／**節が空でないか**／12ヶ月そろっているか／
  `.md` に手書きした HTML が**生タグとして漏れていないか**／プレースホルダの**制御文字が残っていないか**／
  ページ内リンクが切れていないか。**いずれも検出できることを、変異を入れて確認済み**。
- **[D] 1行の長さ** … 手順書に「長く書かない」と書いても長くなる。**書いた直後にその行だけを見て問う**
  仕組み（エディタ側のフック）と、**セッション単位の棚卸し**の2段。**禁止ではなく「その長さは本当に要るか」を問い**、
  要ると判断したら黙らせる印を付ける。効果の実測＝ある1行を312字→60字にして、**表の行の高さ 474px → 84px**。
- **[E] 文体と内部語の露出** … **書き手の運用（章の構成・色分け・根拠の強弱）を地の文に書かない**、
  **内部運用の語を公開ページ本文に出さない**の2つ。後者は**引用行だけを落とす仕組みでは足りない**
  ——**見出し・本文に書いた分は素通りする**（機械化した初回に実際に2件出ていた）。
  **仕組みを説明する節だけは除外する**（そこは内部の語が出るのが正しい）。

**[A]〜[E] はどれも「エラーを出さずに壊れる」**。テストを書く順番に迷ったら、
**例外を投げない失敗から先に**機械化するとよい。

**設計上の要点（再現する人へ）**:

1. **生成を決定的にする**。同じ入力から1バイトも違わない HTML が出るようにしておくと、
   **編集の前後で差分が取れる**。とくに**見出し（節）の一覧**を前後で比べると、
   **節がまるごと消えた事故**が一発で分かる（実際に2回やった）。
2. **「黙って空になる」経路を数えておく**。決まった書式に依存する専用レンダラは、
   書式を崩しても**例外を投げずにその節が空になる**。**エラーで落ちる失敗より危ない**。
3. **止めるものと、警告に留めるものを分ける**。**発行を止めるのは無害チェックと日付ゲート**
   （TODO の「今日」が実日付とズレていたら発行させない）**の2つだけ**。
   噛み合わせ（[A]〜[C]）は**公開の安全とは別軸**なので、止めずに毎回見える所へ出す。
4. **文章のルールで守られなかった箇所から順に機械化する**。この repo はその順で増やしてきた
   （1行の肥大 → 整合性チェック／日付のズレ → 日付ゲート／結合点 → [A]〜[C]）。
5. **見た目は推測せず測る**。表がつぶれているかは、ブラウザで実際に描画して
   **横スクロールが起きているか**を数値で見る。**起きていなければ、表は親の幅に押し込まれてつぶれている**。
   「たぶん直った」で3回外した。
6. **抜け道を作らない**。ゲートを迂回する引数を用意しない。急いでいる時に必ずそこを通る。

**残っている手作業**（機械化していないと明示しておく）: 余白・行の高さ・読みやすさの判断そのもの／
変換層を触った時の前後差分（基準を撮る必要があるため）／専用レンダラの書式検査は「数が揃っているか」まで。

## 7. 「10年運用」への論点（設計の叩き台）

**強み（そのまま活かす）**
- データが **Markdown＝プレーンテキスト**＝フォーマット寿命が長い（ベンダーロックインが無い）。
- **Git** が履歴・監査・分散バックアップを兼ねる。
- 生成は **純 Python＋標準ライブラリだけ**（外部パッケージ依存ゼロ。Markdown→HTML 変換も自前の最小実装）
  ＝環境を選ばず、10年後もそのまま動く見込みが高い。
- 記録/分析の作業は **AI エージェント＋手順書（CLAUDE.md）** に集約＝人の手順ミスを構造的に防ぐ。

**弱み・検討余地（一緒に設計したい所）**
- 写真バイナリの肥大（Git LFS／外部ストレージ／EXIF の位置情報自動除去）。
- 位置情報の秘匿運用の徹底（無害ゲートの網羅性・レビュー）。
- AI エージェント依存（手順書を厚くして「別の AI でも再現できる」状態を保つ）。
- 検索性（現状 noindex）＝内部用の全文検索／RAG インデックスを別立てする余地。
- TSV の時系列が伸びた時のクエリ性（軽量 DB or Parquet への段階移行）。
- ローカル前提（`context.md`）は枠を作ったが、**中身の解像度がまだ低い**
  （「余っている」までは書けても数量は現物確認待ち。畝ごとの乾きやすさ等も未記入）。
  ここが埋まるほど提案の精度が上がるので、**気づくたびに1行足す運用**にしている。
  なお**「無いもの」を書き残すのも同じくらい効く**（一般論の定番資材が手元に無いと分かれば、それ前提の案を最初から捨てられる）。

## 8. 改造を提案する前に（他の AI が繰り返し誤読する点）

この README を読んだ AI は、しばしば次を「改善案」として出す。いずれも**既にそうなっている**か、
**理由があって採らなかった**選択なので、提案の前にここを確認してほしい。

| よく出る提案 | 実態 / 採らない理由 |
|---|---|
| 役割別の名前へディレクトリ再構成（知識・実装・公開物を分ける等） | **役割は現構成と同じ**。名前を変えても機能は増えず、allowlist・整合性チェック・発行スクリプト・エディタ連携が**実パスに依存**しているので壊れるだけ。ゼロから作る人は好きな名前でよいが、この repo では変えない |
| 「どの LLM でも使えるよう汎用化」 | **既に汎用**。データは素の Markdown ＋ TSV、生成は標準ライブラリの Python のみ。AI 用の手順書は名前が特定 CLI 向けなだけで、中身は普通の Markdown＝他の AI もそのまま読める |
| 写真を `photos/` に置き Markdown から参照 | 内部では既に日付＋作物名で保存している。ただし**公開ページには画像を一切出さない**（denylist で遮断）。写真は EXIF に**位置情報**を含むため、公開側に載せる提案は**この仕組みの目的と逆行**する。記録は「写真より事実の言語化」を優先 |
| 経験知を溜める `garden_memory.md`（catch-all メモリ）を追加 | **半分は既存・半分は正しい指摘だった**。失敗と原因→`lessons.md`／判断の閾値→`temp-signals.md`／気温傾向→`thermal.md`／品種の実績→`varieties.md` に**役割別で分割済み**（catch-all にすると同じ知識が2箇所に増えて腐る）。ただし**「一般論と違うこと」＝環境依存・手元資源・作業者の癖だけは置き場所が無かった**ので `context.md` として1枚追加した（§3 の ★）。**足すなら役割を1つに絞る**こと |
| GitHub Actions / Codespaces でスマホ運用を可能に | **★この指摘は正しかったので 2026-07-30 に採り入れた**（この表で唯一「採らない」から「採った」へ変わった項目）。以前は「CLI のクラウド実行で完結するので CI は依存と秘匿リスクが増えるだけ」としていたが、**実際には公開 repo がセッションのスコープ外で 403 になり発行できない**という穴があった。**発行だけを CI に持たせ、生成・無害チェックはローカルと同一スクリプトのまま**にすれば、依存は増えず穴が閉じる（§5 に条件を明記）。**Codespaces は依然不要** |
| 分析は「LLM ＋ Python」で十分 | **ここを一般化すると仕組みの中心が消える**。判断は LLM の推論ではなく、**実測 TSV から積算温度(GDD)を較正して収穫日を逆算する数値モデル**が担う（§3）。「夏まきで間に合うか」に月日でなく**条件**で答えられるのはこの部分。汎用の RAG に置き換えないこと |

**ゼロから再現する人へ**: 上の表は「この repo をどう改造するか」の話。**自分の庭で作り直すなら、
ディレクトリ名もファイル分割も自由**でよい。移植する価値があるのは次の4点だけ:

1. **正本は Markdown**（追記専用のログ ＋ 役割で分けた分析ファイル。DB もフレームワークも要らない）
2. **判断を実測データで数値化する**（体感でなく、気温・日照・降水と積算温度で逆算する）
3. **「一般論と違うこと」を1枚にまとめ、最優先で読ませる**（§3 の ★）＝環境依存・手元資源・作業者の癖。
   これが無いと LLM は教科書解に流れ、**余っている資材を無視し、現場で実行できない提案**をする。
   **判断・選択肢・最終意思決定はここで決まる**。ファイルを置くだけでなく**手順書の冒頭で読ませる導線**まで作ること
4. **公開は生成物だけ**・**allowlist ＋ denylist の2段ゲートを迂回しない**（ここが安全に共有できる根拠）
5. **公開 repo に履歴を残さない**（親を持たない単一コミットで force-push）
